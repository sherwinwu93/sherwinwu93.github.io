* 1.企业为什么需要AI及难以落地?
让模型处理语言,让业务系统掌握事实和执行规则,并检查模型的回答是否正确

在已有的Java系统中,哪些事情给模型,哪些事情给代码?
例子: Spring Boot系统增加智能客服
"昨天买的显示器今天就黑屏了,帮我看看能不能退."
系统工作: 模型生成的内容,经过业务系统验证,才能成为可执行的业务动作
- 理解用户在描述产品故障~申请退货
  LLM: 用户表达难以用关键词覆盖
- 查询订单~签收时间
  Java服务+数据库: 准确~实时的业务事实
- 判断订单是否满足退货规则
  Java业务逻辑: 规则必须明确且可测试
- 把判断结果组织成易懂的回复
  LLM: 擅长处理和生成自然语言
- 创建售后单
  Java服务: 需要鉴权~事务~幂等和审计
** 怎么让模型知道公司业务知识?
三种方式:
1. 提示词与上下文: 在请求中提供要求~资料
   【任务要求】
    你是售后助手，请根据下面提供的资料回答用户。
    资料不够时，说明缺少什么，不要猜测。
    
    【公司退货规则】
    签收后 7 天内，出现质量问题可以申请退货。
    
    【订单资料】
    商品：显示器
    签收时间：3 天前
    用户描述的故障：无法开机
    
    【用户问题】
    我的显示器能退吗？
2. RAG: 先找相关资料,把资料交给模型回答
3. 微调(改模型): 使用训练样本继续训练模型
** Java服务应该如何组织?
智能售后
1. Controller
2. AfterSalesService
   1. IntentExtractor: 模型提取用户诉求
   2. OrderService: 鉴权并查询订单
   3. ReturnPolicyService: 执行业务规则
   4. ReplyGenerator: 模型组织回复

#+begin_src json
  {
  "productName": "显示屏",
  "problem": "黑屏",
  "requestType":"RETURN"
  }
#+end_src
模型提取用户的输入,可能存在的问题:
- 商品名称并不和用户订单一致
- RETURN需要校验是允许的类型
- 缺失订单信息时,需要补充信息 或 查询候补订单
- 真正执行退货时, 仍然走已有的权限和业务校验
** 接口返回200,不代表AI功能成功?
比如问订单是否发货了,AI回答发货了(实际没有发),则AI功能失败了.
* 2.新类型的应用
模型~Java~文档检索需要分工. 分工明确后,模型这个组件该怎么用?
** 模型生成回答
   问题+相关资料->模型计算->逐步生成回答(一小段一小段)
** 模型相关参数
1. Token: 模型处理文字的单位(字~词~片段)
   不等于字数
2. 上下文窗口: 模型一次能处理的Token范围
   如果合同够长~聊天历史太多,应用需要:
   - 只取相关段落
   - 对历史聊天记录摘要
   - 把大任务拆成小任务
   模型看到了资料,并不会存储到自身
3. temperature: 越小,答案变化越小
** 常见问题及关注点:
1. 不知道公司政策 - 是否正确提供资料
2. 回答格式不符合要求 - 指令~结构化输出与程序校验
3. 回答变化太大 - 生成参数与任务设计
4. 理解不了业务问题 - 模型能力~输入表达和示例
** 模型的不同"岗位"
AI模型不只有聊天模型
模型类型,与输入输出
- 生成模型: 问题和政策; 一段回答
- 分类模型: 用户投诉; "质量问题""物流问题"等类别
- Embedding模型: 一段文字; 向量
- 图像模型: 商品照片和问题; 对图片的分析或描述
** 模型参数量大,意味着什么?
模型名称有7B,代表有70亿个参数
** 模型不会做某项任务,如何改善?
1. 回答太长: 修改指令(提示词工程)
2. 不知道公司新发布的退货政策: RAG检索新政策,把相关内容放进请求
3. 有大量标注好的业务样例,希望调整模型处理某类任务的表现(fine-tuning)
** 如何选模型? 先拿业务题目测试
拿一批实际问题测试:
- 是否理解正确
- 是否根据资料回答
- 资料不足时是否会追问
- 是否生成错误的事实或操作建议
- 速度和成本是否满足要求
