* 1.企业为什么需要AI及难以落地?
让模型处理语言,让业务系统掌握事实和执行规则,并检查模型的回答是否正确

在已有的Java系统中,哪些事情给模型,哪些事情给代码?
例子: Spring Boot系统增加智能客服
"昨天买的显示器今天就黑屏了,帮我看看能不能退."
系统工作: 模型生成的内容,经过业务系统验证,才能成为可执行的业务动作
- 理解用户在描述产品故障~申请退货
  LLM: 用户表达难以用关键词覆盖
- 查询订单~签收时间
  Java服务+数据库: 准确~实时的业务事实
- 判断订单是否满足退货规则
  Java业务逻辑: 规则必须明确且可测试
- 把判断结果组织成易懂的回复
  LLM: 擅长处理和生成自然语言
- 创建售后单
  Java服务: 需要鉴权~事务~幂等和审计
** 怎么让模型知道公司业务知识?
三种方式:
1. 提示词与上下文: 在请求中提供要求~资料
   【任务要求】
    你是售后助手，请根据下面提供的资料回答用户。
    资料不够时，说明缺少什么，不要猜测。
    
    【公司退货规则】
    签收后 7 天内，出现质量问题可以申请退货。
    
    【订单资料】
    商品：显示器
    签收时间：3 天前
    用户描述的故障：无法开机
    
    【用户问题】
    我的显示器能退吗？
2. RAG: 先找相关资料,把资料交给模型回答
3. 微调(改模型): 使用训练样本继续训练模型
** Java服务应该如何组织?
智能售后
1. Controller
2. AfterSalesService
   1. IntentExtractor: 模型提取用户诉求
   2. OrderService: 鉴权并查询订单
   3. ReturnPolicyService: 执行业务规则
   4. ReplyGenerator: 模型组织回复

#+begin_src json
  {
  "productName": "显示屏",
  "problem": "黑屏",
  "requestType":"RETURN"
  }
#+end_src
模型提取用户的输入,可能存在的问题:
- 商品名称并不和用户订单一致
- RETURN需要校验是允许的类型
- 缺失订单信息时,需要补充信息 或 查询候补订单
- 真正执行退货时, 仍然走已有的权限和业务校验
** 接口返回200,不代表AI功能成功?
比如问订单是否发货了,AI回答发货了(实际没有发),则AI功能失败了.
